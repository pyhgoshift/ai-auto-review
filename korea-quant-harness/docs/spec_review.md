# 운영 명세 v2.0 종합 검토 및 수정 사항

> 대상: "KOREA AUTONOMOUS QUANT TRADING SYSTEM v2.0" 운영 명세
> 결론 요약: 명세의 **방향(생존 우선·AI 권한 분리·fail-closed)은 매우 좋다.** 다만 그대로 구현하면 생기는 **모순 6건과 구조적 위험 8건**이 있어, 이를 고쳐서 구현했다. 수정한 내용은 모두 코드와 테스트에 반영되어 있다.

## 1. 이 명세를 쓴 사람이 실제로 원하는 것 (겉으로 드러나지 않은 의도)

| 겉으로 드러난 요구 | 그 뒤에 있는 의도·우려(추정) | 설계에 반영한 방식 |
|---|---|---|
| "AI는 자금을 움직일 권한이 없다" | AI의 그럴듯한 오판·환각이 실제 손실로 이어지는 것에 대한 강한 경계 | AI 계층(`research/`, `reflex/`, `review/`)이 주문 계층을 **import조차 못 하게** 정적 테스트로 강제 |
| 24/7 자율 운영 | 사람이 화면을 보지 않아도 돌아가는 시스템을 원함 | 그러나 "자율"과 "운영자 승인"이 충돌 → **감시·리서치는 자율, 위험 증가는 승인 필요**로 분리 |
| 수천 줄의 상세 규칙 | 실패를 미리 막고 싶은 마음, 동시에 **"명세가 완벽하면 수익이 날 것"이라는 기대가 섞였을 가능성** | 문서에서 분명히 밝힘: **명세의 완성도는 수익성을 입증하지 않는다.** 현재 검증된 우위는 0이다 |
| 0.80 확률, Quarter Kelly 등 구체 숫자 | 숫자가 있어야 통제된다는 감각 | 숫자는 설정 파일로 옮기고 `UNAPPROVED`로 출하 → **운영자가 근거를 갖고 승인해야만 동작** |

| **지금 구현·검증 가능** | Pydantic 스키마, 진입 게이트, 상태 엔진, 호가 계산, 위험 엔진, 킬 스위치, 동시호가 게이트, 캘린더, OMS 상태 머신, 모의 브로커, 대사, 이벤트 저장소, Brier/ECE, 배포 게이트, 인젝션 방어 | **구현 + 56개 테스트 PASS** (`docs/test_evidence.md`) |

## 3. 치명적인 설계 결함과 수정 (심각한 순서)

### D1. 0.80 확률 임계값이 비용 구조와 맞지 않음 — 사실상 영구 NO-TRADE이거나, 보정을 부풀리게 됨
- **문제**: 매도세 약 20bps + 수수료 + 스프레드 + 시장충격을 합한 왕복 비용은 시연 기준 약 **41bps** [예시 데이터]다. 1~2분 예측 구간에서 "보정된 승률 > 0.80"을 만족하는 신호는 현실적으로 거의 없다. 그 결과 (a) 시스템이 영원히 거래하지 않거나, (b) 임계값을 넘기려고 보정을 느슨하게 하는 유인이 생긴다(Goodhart의 법칙).
- **추가 문제**: 확률만으로는 손익비를 반영하지 못한다. 승률 0.81에 손익비 0.2인 전략은 손실을 낸다.
- **수정**: 주된 기준을 **"비용 차감 순기대값의 보수적 하한 > 안전여유(`min_net_ev_margin_bps`)"**로 바꾸고, 승률 추정에는 Wilson 하한을 쓴다. 0.80은 보조 게이트로만 남겼다(명세의 T01/T02는 그대로 통과).
- **비즈니스 함의**: 데이트레이딩보다는 **수일~수주 보유하는 펀더멘털·수급 전략**이 비용 대비 우위를 가질 가능성이 높다. 로드맵에서 전략 우선순위를 그렇게 조정할 것을 제안한다(§6).

### D2. "주문 경로는 하나뿐" vs "청산은 별도의 안전 경로" 모순
- **수정**: 주문 관리 엔진(OMS)은 하나로 두고, **승인서를 ENTRY(위험 증가)와 REDUCE(청산 전용)로 분리**했다. 킬 스위치·데이터 장애·손실 한도는 ENTRY만 막는다. REDUCE는 "보유 수량 이하"라는 불변조건만 지키면 통과한다(T15: 손실 한도에 도달해도 청산은 승인됨).

### D3. 사전 검사와 실제 제출 사이의 경쟁 상태(TOCTOU)
- **문제**: "제출 직전 재검증"이라고만 쓰여 있고, 구조로 강제하는 장치가 없다.
- **수정**: 위험 엔진이 **1회용·2초 만료 승인서**를 발급한다. OMS는 제출 직전 `redeem()`으로 모든 전역 조건을 다시 확인한다. 위험 예산은 `asyncio.Lock` 하에서 원자적으로 예약된다(동시 20건 요청 테스트에서 한도 초과 0건).

### D4. 타임아웃 시 중복 주문
- **문제**: KIS가 클라이언트 주문키(멱등성 키)를 지원하는지 확인되지 않았다.
- **수정**: 재전송을 **스키마 수준에서 금지**했다(`max_submit_retries`는 0만 허용). 타임아웃이 나면 상태를 UNKNOWN으로 두고, 브로커 주문 목록과 (종목·방향·수량·가격·시각)으로 매칭해 대사한다. 후보가 둘 이상이면 자동으로 킬 스위치를 켠다. 두 번 조회해도 브로커에 주문이 없을 때만 REJECTED로 확정한다.

### D5. Kelly의 p가 어디서 오는지 혼동될 위험
- **문제**: 신호별 `calibrated_prob`를 Kelly 공식에 넣으면 과신이 포지션 크기로 그대로 증폭된다.
- **수정**: Kelly는 **전략 단위의 실증 통계와 Wilson 하한**만 받도록 했다. 신호 확률은 Kelly 계산에 들어가지 않는다.

### D6. 15:15 정책의 구멍
- **문제**: 명세는 "데이트레이딩 신규 진입"만 차단한다. 그래서 오버나이트 전략이라는 이름표만 붙이면 15:15~15:20에 새로 진입할 수 있다.
- **수정**: 기본값을 **모든 신규 진입 차단**으로 했다(설정으로 완화 가능). 기준 시각은 하드코딩하지 않고, 캘린더의 동시호가 시작 시각에서 역산한다(특별 거래일 T21).

### D7. "모름"을 "정상"으로 취급할 위험
- **수정**: 거래정지, 투자경고, VI 상태를 True/False/None 3단계로 두고, **None(미확인)은 차단**한다. 캘린더 범위 밖의 날짜는 UNKNOWN으로 처리해 차단한다.

### D8. 야간 자가개선의 다중 비교 문제
- **문제**: 매일 변형안을 시험하면, 우연히 좋아 보이는 변형이 반드시 나온다(data snooping).
- **수정**: 제안마다 `n_variants_tried`를 기록하게 했고, 배포 게이트는 모든 단계 PASS, 운영자 승인, 산출물 해시 일치, 위험 한도 확대 별도 승인을 모두 요구한다(T20). 백테스트 단계에서는 시도 횟수를 반영해 Sharpe를 보정해야 한다(Deflated Sharpe 등, GATE 5).

### 그 밖의 위험 (중요도 중간)
| ID | 문제 | 수정 |
|---|---|---|
| D9 | SYSTEM 1에서 1~60초마다 LLM을 호출하면 지연, 비용, 비결정성이 생긴다 | 결정론적 기준선을 기본으로 함. 기준선의 `calibrated_prob=0.5`로 **보정 없이는 절대 진입하지 않음**. LLM은 SYSTEM 2 전용이며, 모델 ID·검증 시각·일일 비용 상한이 없으면 호출 금지 |
| D10 | 설정 파일이 있다는 사실만으로 승인된 것처럼 간주될 수 있다 | `approval.status`(UNAPPROVED/PAPER_APPROVED/LIVE_APPROVED)를 모드별로 검사. 저장소에는 **UNAPPROVED**로 출하 |
| D11 | 모의 체결이 낙관적이다 | 지정가는 체결가가 지정가를 **관통**할 때만 체결된 것으로 본다(대기열 위치를 모르므로) |
| D12 | **법·규제 리스크가 명세에 없다** | 증권사 API 약관의 자동주문 허용 범위, 알고리즘 거래 관련 거래소·감독 규정, 잦은 정정·취소가 허수성 주문으로 오인될 위험을 **GATE 1 확인 항목**으로 추가(api_inventory §7) |
| D13 | 세율, 거래시간, 호가단위가 바뀔 수 있다 | 모두 `verified: false`로 두고, LIVE에서는 차단 |
| D14 | 운영자가 한 명뿐이다 | 킬 스위치가 켜진 상태에서 운영자와 연락이 안 되면 보유 포지션이 오버나이트로 노출된다 → runbook에 부재 시 정책을 결정하도록 요구(GATE 1 결정 항목) |

## 4. 당연하게 여긴 전제를 의심해 보기

| 전제 | 의심 | 판단 |
|---|---|---|
| "AI가 판단하면 사람보다 낫다" | 공개 데이터 기반 LLM 판단은 다른 참여자도 거의 동시에 할 수 있다 | AI의 가치는 **판단의 정확도보다 처리량과 일관성**에 있다. 알파는 실증으로만 인정한다 |
| "초단기 미시구조 신호가 우위의 원천" | 개인 API 환경(수십~수백 ms 지연)이 코로케이션 참여자보다 빠를 수 없다 | 미시구조 우위는 **가장 가능성이 낮다**. 체결 품질(EXECUTION EDGE)은 비용 절감 수단으로만 활용 |
| "모의투자가 잘 되면 실거래도 된다" | 모의 체결은 대기열·시장충격·부분체결을 과소평가한다 | 낙관적이지 않은 체결 모델을 쓰고, 소액 LIVE에서 체결 괴리를 따로 측정한다 |
| "24/7 운영이 필수" | 한국 주식은 거래 가능 시간이 제한적이다 | 장외 시간에는 리서치·대사·평가만 한다. 상시 주문 프로세스는 위험만 늘린다 |
| "시스템을 만들어야 한다" | **반대로 생각하면**: 지수 ETF를 보유하는 것도 하나의 선택지다 | 모든 전략은 **KOSPI200 보유 대비 초과 위험조정수익**으로 평가해야 한다(GATE 5 기준으로 제안) |

## 5. 세 가지 관점에서 비교

| 관점 | 강점 | 위험·공백 | 권고 |
|---|---|---|---|
| **사업관리** | 6단계 게이트와 증거 중심 승인 체계가 명확하다 | 범위가 매우 크다(데이터 4종, 브로커, 모델 2계층, 백테스트). **주요 일정 경로 = KIS API 검증과 시점별(point-in-time) 과거 데이터 확보**. 과거 호가 데이터는 확보가 어려울 수 있어, 확보하지 못하면 앞으로 수집해야 하고 이는 **수개월**이 걸린다. 운영자가 한 명이라는 점도 병목이다 | 최소 범위: LLM 없이 GATE 1~4를 먼저 완료. 데이터 수집은 GATE 2 직후부터 바로 시작(보정 표본을 쌓는 데 시간이 걸리므로) |
| **기술** | fail-closed, 승인서 기반 단일 경로, 해시 체인 감사 로그, 상태 머신을 이번에 구현·테스트함 | 브로커 어댑터, 실시간 수신, 백테스트 엔진이 미구현이다. 단일 프로세스·asyncio 구조라 주문 프로세스와 리서치 프로세스의 물리적 분리는 GATE 2에서 설계해야 한다. 내부 장부는 수수료·세금을 반영하지 않으므로 현금 대사가 필요하다 | GATE 2에서 프로세스 분리(주문 프로세스는 최소 권한), 현금 대사, 시각 동기화 연동을 설계 |
| **비즈니스** | 생존 우선 원칙이 개인 자본에 적합하다 | **비용 장벽**: 왕복 약 0.4%[예시]. 일 1회 회전이면 연 약 100%의 비용 부담이다. API 비용(SYSTEM 2)과 데이터 비용도 수익에서 빠진다. 기회비용은 지수 보유다 | 보유기간을 늘리고 회전율을 낮추는 쪽으로 전략을 재설계. 승인 기준에 "비용 차감 후 벤치마크 대비 초과" 포함 |

**종합**: 기술적으로는 "안전하게 거래하지 않는 시스템"을 지금 바로 만들 수 있고, 이번에 만들었다. 비즈니스적으로는 "수익을 내는 시스템"인지는 데이터가 쌓이기 전까지 알 수 없다. 따라서 **현재 등급은 A. RESEARCH ONLY**이고, 다음으로 가장 가치 있는 일은 코드보다 **데이터 확보와 API 검증**이다.

## 6. 수정 반영 후 전략 로드맵 제안 (운영자 판단 필요)

1. **1순위**: 펀더멘털+수급 기반 스윙(수일~수주). FUNDAMENTAL EDGE를 검증하고, 실행은 지정가 분할로 비용을 최소화한다.
2. **2순위**: 이벤트(확정 공시) 반응 전략. 공개 시각(`available_at`)을 엄격히 지켜야 한다.
3. **보류**: 1~2분 예측 구간의 미시구조 데이트레이딩. 비용 차감 우위가 실증되기 전까지는 구조만 유지한다.

## 7. 이 결론이 틀릴 수 있는 지점 (자기 점검)

| 내 판단 | 틀릴 수 있는 이유 | 대응 |
|---|---|---|
| 미시구조 데이트레이딩의 우위 가능성이 낮다 | NXT·KRX 간 유동성 이동이나 동시호가 불균형처럼 **한국 고유의 구조적 비효율**이 있을 수 있다 | 보류이지 폐기가 아니다. 데이터가 쌓이면 같은 게이트로 재평가 |
| 15:15 이후 전면 차단 | 지나치게 보수적이라 기회를 놓칠 수 있다 | 설정으로 완화 가능. 대신 운영자 승인 필요 |
| 세율·거래시간·호가단위 값 | **내가 입력한 값이 틀렸을 수 있다**(특히 2026-09 이후 바뀐 제도) | 모두 `verified: false`로 두었고, LIVE는 검증 전 차단. GATE 1에서 공지 원문과 대조 필수 |
| 왕복 비용 약 41bps | 수수료(1.5bps)와 충격 계수는 예시값이다 | 실제 증권사 요율과 체결 데이터로 재추정 |
| 이 코드가 안전하다 | 테스트는 **내가 상상한 실패**만 검증한다. 데이터 장애와 주문 장애가 동시에 오는 경우, 브로커가 비정상 응답(부분 응답, 필드 누락)을 주는 경우는 아직 실제 API로 시험하지 못했다 | GATE 4에서 실제 모의투자 API로 장애 주입 테스트 |
| 정적 import 검사로 AI와 주문 계층이 분리되어 있다 | 같은 프로세스라면 동적 import나 리플렉션으로 우회할 수 있다 | GATE 2에서 **프로세스·자격증명의 물리적 분리** 필요(논리 분리만으로는 부족) |

### 빠뜨렸을 수 있는 위험
- 증권사 API의 토큰 만료가 장중에 일어나는 경우 → 인증 실패 플래그 경로는 있으나 실제 연동 테스트는 없다.
- 시각 동기화(NTP) 실패 → 헬스체크 함수만 있고 실제 시각원 연동은 없다.
- 신규 상장, 종목코드 변경, 액면분할 당일의 가격 연속성 → 데이터 계약에는 있으나 처리 코드는 없다.
- 운영자 승인 기록 자체의 위변조 → 현재는 파일 기반이다. 서명·이중 승인은 GATE 6 전에 검토가 필요하다.
