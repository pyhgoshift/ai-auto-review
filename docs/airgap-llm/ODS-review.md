# Osmantic/ODS 검토 — 우리 폐쇄망 LLM 구축과의 관련성

> 검토 대상: https://github.com/Osmantic/ODS (`main` @ 2878317, 2026-10-14)
> 검토 범위: README, ARCHITECTURE, `ods/docs/`(OFFLINE_AND_MIRRORING, M1-OFFLINE-MODE, MACOS-QUICKSTART, KNOWN-GOOD-VERSIONS, MODEL-TERMS-INVENTORY), `extensions/services/llama-server/README.md`, `config/model-library.json`, `installers/macos/install-macos.sh` 일부
> 전체 코드(5,588개 파일)를 감사한 것은 아니며, 문서와 설치 스크립트의 핵심 경로만 확인했습니다.

## 결론
**관련성은 높습니다. 다만 "도입할 제품"이 아니라 "근거 자료와 절차를 차용할 대상"입니다.**
- **차용할 것:** 같은 계열 27B 하이브리드 모델의 실측 데이터, llama.cpp 버전별 함정, 반입 기록(receipt)·해시·라이선스 관리 방식
- **도입하지 않을 이유:** ODS의 "오프라인"은 *온라인으로 설치한 뒤 망을 끊는 것*이고, 우리는 *처음부터 망 밖에서 설치*해야 합니다. 또 Docker Desktop과 20여 개 서비스가 딸려 와서 반입·심의 부담이 수십 배로 늘어납니다.

## 1. ODS는 무엇인가 (사실)
- 로컬 AI 서버 스택 설치기: llama-server(llama.cpp) + Open WebUI + 대시보드 + LiteLLM + 음성 + RAG + n8n + 에이전트 등. 24개 서비스 매니페스트로 구성
- Mac: llama-server는 **네이티브(Metal, GGUF)**로 돌고, 나머지는 Docker Desktop 컨테이너로 돕니다(이미지 약 10GB)
- Windows: WSL2 + Ubuntu + Docker Desktop(winget으로 설치) 경로
- 라이선스: Apache 2.0 + "Pixel ODS-only"(별도 조건)
- 상태: V3 **프리릴리스**. 설치기는 서명되지 않은 `main` 브랜치를 받으며, "검증된(서명) 채널을 통과한 릴리스는 아직 없음"이라고 스스로 밝히고 있습니다

## 2. 우리 구성과의 대조
| 항목 | 우리 계획 | ODS | 의미 |
|---|---|---|---|
| Mac 엔진 | LM Studio + MLX | 네이티브 llama.cpp(GGUF, Metal) | ODS는 우리의 "GGUF 예비 노선"과 같은 길. MLX 관련 근거는 ODS에 없음 |
| Windows 엔진 | llama.cpp CUDA 단독 실행 | WSL2 + Docker + CUDA 컨테이너 | ODS 쪽이 의존성이 훨씬 많음. 연습용으로도 실전과 더 멀어짐 |
| 모델 | "Qwen3.8-27B" | Qwen3.5-27B(기본 후보), Qwen3.6-27B(후보) | 같은 아키텍처의 실측값이 있음 |
| 오프라인 | 처음부터 망 밖에서 반입·설치 | `--offline` = 온라인 설치 후 분리. **macOS 설치기에는 이 옵션 자체가 없음** | 그대로 쓸 수 없음 |
| 반입 기록 | SHA256 매니페스트 | 모델별 고정 리비전 URL + sha256, 이미지 다이제스트 고정, 오프라인 receipt 양식 | 그대로 차용할 가치가 큼 |
| 라이선스 | LICENSE 동봉 | 58개 모델의 라이선스 출처 인벤토리 | 심의 서류 작성 방식으로 차용 |

## 3. 우리 가이드에 영향을 주는 발견
1. **모델명과 사양 근거 확보:** ODS 카탈로그의 Qwen3.6-27B 항목은 다음과 같습니다.
   - 64개 레이어 중 4번째마다 KV 헤드 4개(즉 어텐션 레이어 16개), 헤드 차원 256
   - 최대 컨텍스트 262,144
   - UD-Q4_K_XL 파일 17.6GB(sha256 고정), 64K 컨텍스트에서 약 21GiB
   - Qwen3.5-27B Q4_K_M은 16.7GB

   "하이브리드 어텐션, 27B, 262K"라는 사용자 설명과 정확히 일치합니다. 따라서 **"Qwen3.8-27B"는 Qwen3.6-27B(또는 3.5-27B)의 오기일 가능성이 높습니다 [가설 — 사용자 확인 필요]**. 기존 가이드에서 추정한 KV 캐시 구조(어텐션 레이어 약 1/4)와 4bit 크기(15~17GB)는 이 데이터로 뒷받침됩니다.
2. **llama.cpp 버전이 성능을 좌우합니다(사실, ODS 실측):**
   - b8210은 프롬프트 체크포인트를 8개만 유지합니다. 그래서 8턴보다 이전 내용을 바꾸면 **프롬프트 전체를 다시 처리**합니다(84.3초 → 체크포인트 32개로 33.4초).
   - 하이브리드 모델의 speculative 체크포인트는 b8842 이상, ngram-mod는 b8955 이상에서 지원됩니다. ODS는 b9014로 고정했습니다.
   - → 기존 가이드에서 "확인 필요"로 남겼던 하이브리드 모델 프롬프트 캐시 문제가 **실제로 존재**한다는 근거입니다. **반입할 llama.cpp 빌드는 b9014 이상**으로 정하는 것이 맞습니다. LM Studio에 내장된 llama.cpp 런타임의 빌드 번호도 같은 기준으로 확인해야 합니다.
3. **추론(thinking) 모드 플래그가 빌드마다 다릅니다:** b9014는 `--reasoning` 기본값이 `auto`라서 생각 과정이 답변에 섞여 나올 수 있습니다. b8248에서는 `--reasoning-budget 0`로만 끌 수 있습니다. 가이드의 "채팅 템플릿/추론 모드 이상" 항목에 대한 구체적 근거입니다.
4. **사전 배치 재사용:** macOS 설치기는 `~/ods/data/models/`에 같은 sha256의 파일이 이미 있으면 다운로드를 건너뜁니다. 이것이 "파일을 미리 반입해 두는" 방식이 통한다는 근거입니다. 다만 **llama-server 바이너리(GitHub), Docker 이미지, 네트워크 점검 단계도 같은 방식으로 건너뛸 수 있는지는 확인하지 못했습니다.**

## 4. ODS를 폐쇄망에 도입하면 생기는 위험
| 위험 | Mac Studio(실전) | Windows 11(연습) |
|---|---|---|
| 반입량 | Docker Desktop + 이미지 약 10GB + 바이너리 + 모델 | + WSL2 + Ubuntu 이미지 + Docker Desktop |
| 설치 경로 | 설치기가 GitHub·HuggingFace·Docker 레지스트리에 접속. Mac용 `--offline` 없음 | winget·WSL 다운로드 전제. 폐쇄망에서는 가장 불리 |
| 보안 심의 | 서비스 20여 개, 서명되지 않은 `main`, 프리릴리스 → "처음 보는 바이너리"가 폭증 | 동일 |
| 라이선스 | Docker Desktop은 일정 규모 이상 조직에서 유료 구독 필요 **[현행 약관 확인 필요]**. Pixel 별도 조건 | 동일 |
| 변경 속도 | 매일 커밋 → 버전 고정·반입 주기와 충돌 | 동일 |
| 성능 | TEI 임베딩이 Mac에서 Rosetta 에뮬레이션으로 동작(느림) | GPU를 WSL에 넘겨주는(passthrough) 계층이 추가됨 |

## 5. 세 관점
| 관점 | 판단 |
|---|---|
| 사업관리 | 반입 품목과 심의 건수가 크게 늘어 일정 리스크가 커짐. 대신 receipt 양식은 심의 서류 품질을 높여 줌 → **양식만 차용** |
| 기술 | 같은 계열 27B 모델의 실측값과 llama.cpp 버전별 함정이 가장 큰 가치. 스택 자체는 Docker 계층 때문에 장애 지점이 늘어남 |
| 비즈니스 | 1인 업무 활용에는 과함. 목표가 "부서 공용 웹 채팅 + 문서 RAG"로 커지면 Open WebUI + llama-server 조합의 참고 설계가 됨 |

## 6. 반대로 생각해 보면 — ODS가 맞는 선택이 되는 경우
- 폐쇄망 안에 **Linux 서버 + 내부 Docker 레지스트리 미러**가 이미 있고, 다수 사용자 서비스가 목표인 경우. 이때는 OFFLINE_AND_MIRRORING 문서의 절차(이미지 미러, 다이제스트 고정, receipt)가 그대로 운영 표준이 됩니다.
- 이 경우에도 반입 단위는 "ODS 전체"가 아니라 **필요한 서비스 2~3개(llama-server, Open WebUI, 필요하면 Qdrant)**로 좁히는 것이 맞습니다.

## 7. 권고
1. **지금은 도입하지 않음.** 현재 목표(맥 1대 실전 운영)에서는 LM Studio 노선이 반입·심의·복구 모든 면에서 단순합니다.
2. **차용(즉시):**
   - 오프라인 receipt 양식을 반입 서류에 반영
   - 모델 기록을 "고정 리비전 URL + sha256 + 라이선스 출처"로 남김
   - llama.cpp 빌드 b9014 이상을 기준선으로 삼음
   - `--ctx-checkpoints 32`, 추론 끄기 플래그 확인 항목 추가
   - KNOWN-GOOD-VERSIONS 방식의 "검증된 버전 표" 작성
3. **가이드 수정 후보:** 모델명 확인 질문에 "Qwen3.6-27B인가?"를 추가하고, GGUF 예비 노선의 근거로 ODS 실측값을 인용

## 8. 자기검증
- 문서와 설치 스크립트 일부만 확인했습니다. 실제 오프라인 설치 가능 여부(바이너리·이미지 사전 배치)는 검증하지 않았습니다.
- ODS의 성능 수치는 RTX 5090과 Mac mini M4 16GB에서 측정한 값입니다. **Mac Studio에서 측정한 값이 아닙니다.**
- LM Studio에 내장된 llama.cpp/MLX 런타임의 빌드 번호와는 직접 비교할 수 없습니다. LM Studio 쪽은 여전히 리허설로 확인해야 합니다.
- Docker Desktop 유료 조건은 기억에 의존한 내용이라 현행 약관 확인이 필요합니다.
- 저장소가 매일 바뀌므로 위 내용은 2026-10-14 커밋 기준입니다.
