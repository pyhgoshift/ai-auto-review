> 대상: Qwen 계열 27B 하이브리드 어텐션 모델, LM Studio(MLX) on Mac Studio, llama.cpp(CUDA·GGUF) on Windows 11

## 0. 먼저 짚을 것 — 빈칸이 판단을 좌우합니다

요청서의 대괄호 항목이 비어 있습니다. 아래 4개는 "참고용"이 아니라 **결론을 뒤집는 변수**입니다.

| 빈칸 | 왜 결론이 바뀌는가 |
|---|---|
| 맥 통합 메모리 GB | 32~36GB면 4bit 양자화 + 32K 컨텍스트가 상한, 64GB면 8bit 가능, 96GB+면 8bit + 장문맥 가능 |
| 윈도우 VRAM GB | 8GB면 27B Q4(약 16~17GB)가 GPU에 다 안 올라감 → 연습 환경의 속도·동작이 실전과 전혀 다름 |
| USB 허용 여부·허용 매체 | FAT32 전용 보안USB면 4GB 넘는 파일을 그대로 못 옮김 → 분할 절차가 필수가 됨 |
| 심의 소요 기간 | 1~2일이면 "부족하면 다시 반입", 2~4주면 "한 번에 완결된 번들"이 절대 조건 |

아래 내용은 이 값이 없을 때를 위해 **조건별로** 썼습니다.

**모델명 확인 필요:** "Qwen3.8-27B"는 작성자가 확인할 수 있는 공개 모델명이 아닙니다(확인 가능한 것은 같은 계열의 하이브리드 어텐션(Gated DeltaNet + Gated Attention) 27B, 262K 컨텍스트 모델). 실제 반입 대상 모델 카드의 `config.json`에서 `architectures` / `model_type`을 꼭 확인하세요. **엔진이 이 아키텍처를 지원하는 버전인지가 이 프로젝트의 최대 기술 리스크**입니다(2단계 참고).

## 1단계 — 문제·목표·장애물 정의

### 문제: 폐쇄망 AI의 근본 제약
폐쇄망의 본질적인 제약은 "인터넷이 없다"는 사실보다 **"현장에서 빠진 것을 확인하는 데 드는 비용이 며칠에서 몇 주 단위"**라는 점입니다.
- 온라인 환경에서는 `pip install`, 자동 업데이트, 드라이버 자동 설치 같은 **보이지 않는 다운로드**가 수십 번 일어납니다. 폐쇄망에서는 이 하나하나가 **반입 심의 1건**이 됩니다.
- 오류가 나도 검색할 수 없습니다. 에러 메시지 해석 자료(문서, 릴리스 노트)도 미리 반입해야 합니다.
- 모델과 엔진은 **같이 움직이는 세트**입니다. 새 아키텍처 모델은 새 엔진 버전을 요구하고, 새 엔진은 새 OS·드라이버를 요구할 수 있습니다.

### 목표: 성공 판정 기준(측정 가능하게)
| 기준 | Mac Studio(실전) | Windows 11(연습) |
|---|---|---|
| 기동 | 네트워크 완전 차단 상태에서 앱 실행 → 모델 로드 → 응답 | 동일 |
| 무결성 | 반입 파일 전부 SHA256 일치(불일치 0건) | 동일 |

| 품질 | 업무 골든셋(정답이 정해진 10~20문항) 통과율 기준 충족 | 동일 골든셋으로 절차만 검증 |
| 복구 | N-1 버전으로 **30분 안에** 되돌리는 절차를 실제로 1회 수행해 봄 | 드라이버/엔진 롤백 실제 수행 |

| 문서화 | 반입 목록·해시·버전·설정값이 기록되어 다른 사람이 재현 가능 | 리허설 결과가 그 문서의 초안이 됨 |

### 최대 장애물: 무엇이 가장 치명적인가
| 후보 | 내 상황에서의 치명도 | 이유 |
|---|---|---|
| **반입 누락 × 심의 지연** | **최상** | 파일 하나 빠지면 심의를 다시 받아야 함. 심의 기간이 길수록 피해가 곱으로 커짐. 다른 모든 장애물이 결국 이 경로로 피해를 줌 |
| 오프라인 의존성(엔진 런타임) | 상 (Mac) | LM Studio의 MLX/llama.cpp **런타임 엔진은 앱과 별도로 온라인 업데이트되는 구조**. 반입한 앱에 들어 있는 런타임이 신규 아키텍처를 지원하지 않으면 모델 로드 실패 **[확인 필요]** |
| 드라이버 불일치 | 상 (Windows만) | Mac에는 GPU 드라이버 개념이 없음(OS에 Metal 포함). 실전 리스크가 아니라 **연습 환경 리스크** |
| 모델 파일 반입 | 중 | 크기(15~55GB)와 매체 파일시스템 제한(FAT32 4GB) 문제. 미리 알면 해결 가능 |
| 업데이트 불가 | 중(단기)·상(장기) | 당장은 문제가 없지만, 6~12개월 뒤 더 좋은 모델이 나오면 "엔진+모델+OS" 동시 교체가 필요 → 반입 주기 설계가 필요 |

**결론:** 실전(Mac) 기준으로 가장 치명적인 것은 **"엔진 런타임–모델 아키텍처 호환성 미검증 상태에서의 반입"**이고, 그 피해를 키우는 것은 **심의 지연**입니다. 드라이버 문제는 Windows 연습에만 해당하는데, 연습에 시간을 많이 쓰게 만들어 오히려 주의를 흩뜨릴 위험이 있습니다.

## 2단계 — 맹점 진단

### 2-1. "USB로 파일만 옮기면 된다"가 위험한 이유
1. **파일시스템 제한:** FAT32는 4GB를 넘는 파일을 담을 수 없습니다. 27B GGUF Q4는 약 16~17GB, MLX 8bit는 약 28~30GB **[가설]**입니다. 보안USB가 FAT32 고정이면 복사가 중간에 실패하거나, 일부 도구에서는 **잘린 파일이 조용히 남습니다**.
   - 해결: exFAT 매체(Mac·Windows 모두 읽기/쓰기 가능) 또는 `llama-gguf-split`로 분할(GGUF), MLX는 safetensors 샤드가 보통 5GB 이하로 나뉘어 있음 **[확인 필요]**. NTFS는 Mac에서 읽기 전용입니다.
2. **"파일"이 아니라 "실행 환경"을 옮기는 일입니다:** 모델 파일 + 엔진 바이너리 + 엔진 런타임 + 설정 프리셋(채팅 템플릿, 샘플링 값) + 문서가 함께 맞아야 동작합니다.
3. **Mac 보안 속성:** 인터넷에서 받은 `.dmg`/`.app`에는 `com.apple.quarantine` 속성이 붙어 있습니다. 공증(notarization) 정보가 앱에 스테이플되어 있지 않으면 오프라인 Gatekeeper 검사에서 실행이 막힐 수 있습니다 **[확인 필요]**. 우회 명령(`xattr`)은 보안 정책 위반이 될 수 있으니 **보안 담당자 승인을 미리 받아 두세요**.
4. **macOS 부산물:** exFAT 매체에 Mac이 `._파일명`, `.DS_Store`를 만듭니다. 해시 목록 검증에서 "모르는 파일"로 걸리거나 심의관이 의심할 수 있습니다.
5. **외부 연결 시도 = 보안 이벤트:** LM Studio 등은 업데이트 확인을 시도합니다. 폐쇄망에서는 실패로 끝나지만, **보안 관제에서 차단 로그(DNS/아웃바운드 시도)가 이상 징후로 잡힐 수 있습니다**. 설정에서 자동 업데이트를 끄고, 관제 측에 미리 알려 두세요.

### 2-2. 의존성이 빠지면 실제로 벌어지는 일
| 누락 항목 | 증상 | 함정 |
|---|---|---|
| Python 패키지(휠) | `ModuleNotFoundError`, 또는 pip가 인터넷 접속을 시도하다 타임아웃 | 휠은 **OS·CPU 아키텍처·Python 버전별로 다름**. Windows에서 받은 휠은 Mac(arm64)에서 쓸 수 없음 |
| CUDA 런타임 DLL (`cudart64_12.dll`, `cublas64_12.dll` 등) | llama.cpp가 **오류 없이 CPU로 대체 실행**되거나 DLL 로드 오류 발생 | 가장 위험한 경우는 "동작은 하는데 10~50배 느린" 상태입니다. 고장이라는 걸 알아채기 어렵습니다 |
| Visual C++ 재배포 패키지 | `VCRUNTIME140.dll을 찾을 수 없습니다`, `0xc000007b` | 개발 PC에는 보통 이미 깔려 있어서 연습에서는 문제가 안 드러나고 **새 PC에서만 터집니다** |
| GPU 드라이버(버전 부족) | CUDA 초기화 실패 → CPU 대체 실행 | `nvidia-smi` 우측 상단의 "CUDA Version"이 llama.cpp 빌드의 CUDA 버전 이상이어야 함 |
| 엔진 런타임(LM Studio) | "Unsupported model architecture" 같은 오류로 로드 실패 | 앱 버전이 아니라 **런타임 버전**을 확인해야 함 |
| 채팅 템플릿 | 로드는 되지만 답변이 이상함(무한 반복, `<think>` 노출, 도구 호출 깨짐) | 기술적 오류가 아니라 **품질 문제로 보이기 때문에** 원인을 찾기가 가장 어려움 |

### 2-3. "Windows 노트북 연습"에 대한 냉정한 평가
| 항목 | 연습이 실전 리스크를 줄여 주는가 | 판정 |
|---|---|---|
| 반입 절차(매체 포맷, 해시 검증, 반입 목록, 심의 서류) | 그렇다. OS와 상관없는 절차입니다 | ✅ 가치 높음 |
| 모델 형식 | 아니다. Windows는 GGUF, Mac은 MLX로 **서로 다른 파일**입니다 | ❌ 연습이 안 됨 |
| 엔진 | 아니다. llama.cpp 단독 실행과 LM Studio(MLX)는 다른 소프트웨어입니다 | ❌ |
| 드라이버·CUDA | 실전에는 없는 문제입니다. 연습 시간의 대부분을 여기에 쓰게 될 수 있습니다 | ⚠️ 시간 함정 |
| 성능·메모리 | VRAM 8~16GB에서 27B는 일부 레이어를 CPU로 내림(오프로드) → 실전과 무관한 수치 | ❌ 오해 위험 |
| 아키텍처 지원 확인 | 일부만. llama.cpp가 하이브리드 아키텍처를 지원하는지는 확인되지만, **MLX 지원은 확인되지 않음** | ⚠️ |
| 잘못된 자신감 | "윈도우에서 됐으니 맥에서도 되겠지" | ❌ 가장 큰 함정 |

**판정:** Windows 연습은 **"반입 절차 리허설"로는 유용하지만, "엔진·모델 리허설"로는 오히려 함정**입니다.

### 2-4. 아직 보지 못한 기회(관점 바꾸기)
1. **실전 장비로 직접 리허설:** Mac Studio가 아직 폐쇄망 밖에 있다면, **Mac 자체를 Wi-Fi·랜선 차단 상태로 두고** 전체 절차를 리허설하는 것이 Windows 연습보다 효과가 10배 큽니다. 이미 망 안에 있다면, 같은 칩 세대의 다른 Mac(MacBook Pro라도)을 리허설 장비로 쓰는 것이 낫습니다.
2. **형식 통일:** LM Studio는 Mac에서도 llama.cpp(GGUF) 엔진을 지원합니다. **같은 GGUF 파일을 양쪽에서 쓰면** Windows 리허설이 모델 파일·템플릿 검증까지 대신해 줍니다. 대신 Mac에서 MLX보다 속도가 다소 떨어질 수 있습니다 **[가설: 생성 속도 기준 0~30%]**. 권장 방식은 **MLX(주력) + GGUF(예비)를 함께 반입**하는 것입니다. 한쪽 런타임이 실패해도 다른 쪽으로 즉시 대체할 수 있어서 **복구 수단 자체가 됩니다**.
3. **장비째 반입:** 기관 정책상 "파일 반입"보다 "준비된 장비 반입(초기화·검사 후)"이 심의가 쉬운 경우가 있습니다. 확인해 볼 가치가 있습니다.
4. **역할 재정의:** Windows 노트북을 "연습 장비"가 아니라 **"반입 번들 제작·검증 스테이션"**(다운로드 → 해시 생성 → 매체 기록 → 재검증)으로 쓰는 편이 더 정확한 용도입니다.

### 3-2. 엔진–형식–하드웨어–매체 묶음
| 묶음 | 엔진 | 모델 형식 | 하드웨어 제약 | 반입 매체 제약 |
|---|---|---|---|---|
| A. 실전 주력 | LM Studio + MLX 런타임 | MLX safetensors (4bit/8bit) | 통합 메모리 × GPU 할당 한도(기본 약 65~75%) | 디렉터리 단위(샤드 다수), exFAT 권장 |
| B. 실전 예비 | LM Studio + llama.cpp(Metal) 런타임 | GGUF | 동일 | 단일 대용량 파일 → FAT32 불가 |
| C. 연습 | llama.cpp CUDA 빌드 | GGUF (B와 같은 파일) | VRAM(부족하면 일부 CPU 오프로드) | 동일 |

→ **B와 C가 같은 파일을 쓰도록 설계하면** 연습의 가치가 크게 올라갑니다.

### 3-3. 사실 / 가설 / 결론
| 구분 | 내용 |
|---|---|
| **사실** | 폐쇄망에서는 인터넷이 없다. 모든 파일은 매체로 반입한다. Mac은 MLX·Metal을 쓰고, Windows는 CUDA를 쓴다. FAT32는 4GB 넘는 파일을 담을 수 없다. GGUF와 MLX는 서로 다른 파일 형식이다 |
| **가설(검증 필요)** | 모델명/아키텍처, 반입할 LM Studio 런타임의 해당 아키텍처 지원 여부, 양자화별 파일 크기, Mac 메모리·Windows VRAM, 262K 컨텍스트가 업무에 정말 필요한지, 하이브리드 모델의 프롬프트 캐시 재사용 동작 |
| **결론** | ① 실전 리허설은 Mac(또는 동급 Mac)에서 해야 한다 ② 번들은 "1회 완결 + N-1 동봉" 원칙으로 만든다 ③ MLX + GGUF를 이중으로 반입한다 ④ 컨텍스트는 32K부터 시작해 단계적으로 늘린다 |

### 3-4. 폐쇄망 구축에서 기억할 5가지
1. **반입은 1회에 끝나야 한다.** 누락 1건 = 심의 1회 추가.
2. **엔진 버전 = 모델 지원 범위.** 모델보다 런타임 버전을 먼저 고정한다.
3. **해시 없이는 반입하지 않는다.** 원본 → 매체 → 대상 장비, 3지점에서 검증한다.
4. **되돌릴 수 있어야 바꾼다.** 모든 변경 전에 N-1 설치본과 백업을 갖춘다.
5. **연습 환경의 성공은 실전 성공의 증거가 아니다.**

### Mac 메모리별 운영안 [가설 — 실측 필요]
27B 하이브리드 모델은 전체 레이어 중 일부(예: 약 1/4)만 KV 캐시를 쓰는 구조라서, 일반 트랜스포머보다 긴 컨텍스트에서 메모리 부담이 작습니다. 아래 수치는 이를 가정한 추정치입니다.

| 통합 메모리 | 권장 형식 | 시작 컨텍스트 | 판단 |
|---|---|---|---|
| 32~36GB | MLX 4bit (약 15~16GB) | 16K~32K | 운영은 가능하지만 다른 앱과 메모리 경합. 8bit 불가 |
| 64GB | MLX 8bit (약 28~30GB) 또는 4bit | 32K → 128K | 업무용으로 적정 |
| 96GB 이상 | MLX 8bit | 32K → 262K | 장문맥 가능. 다만 긴 프롬프트의 **입력 처리(prefill) 시간이 수 분 단위**가 될 수 있음 |

### 어떤 정보가 있으면 판단이 바뀌는가
| 정보 | 바뀌는 판단 |
|---|---|
| 심의 기간 ≥ 2주 | MLX + GGUF 이중 반입, N-1 동봉, 문서 동봉이 **필수**로 바뀜 |
| USB 불가, CD/DVD만 허용 | 모델 반입 전략 전면 수정(분할 + 다수 디스크) 또는 장비째 반입 검토 |
| Mac 메모리 32GB | 4bit 고정, 장문맥 목표 포기, 8bit 반입 불필요 |
| Windows VRAM ≥ 24GB | Windows가 성능 비교 기준선으로 의미를 갖기 시작함 |
| 다수 사용자 API 서비스 | LM Studio보다 서버형 구성 검토, 접근통제·로그 요구사항 추가 |
| 모델이 아직 MLX 미지원 | Mac에서도 GGUF(llama.cpp 런타임)가 주력이 됨 |

### 세 관점 비교와 종합
| 관점 | 무엇이 보이는가 | 숨은 의도·감정 |
|---|---|---|
| 사업관리 | 일정 리스크의 대부분은 기술보다 **심의 왕복**. 일정표에 "재반입 1회" 버퍼를 넣어야 함 | 보안 담당자는 "처음 보는 바이너리"를 최소화하고 책임 소재를 명확히 하고 싶어 함 → 반입 목록·해시·출처·라이선스를 갖춘 서류가 심의 기간을 줄이는 지렛대 |

| 비즈니스 | 262K 컨텍스트, 최신 모델은 "있으면 좋은 것"이고, 성공 여부는 **업무 골든셋 통과율과 가동률** | 의사결정자는 가시적 성과를 원함 → 첫 반입은 작은 범위(32K, 한두 개 업무)로 빨리 성과를 내는 편이 다음 반입 승인에 유리 |

**종합:** 기술적으로 가장 어려운 부분과 프로젝트를 실패하게 만드는 부분이 다릅니다. 실패는 대부분 **"반입 1회 완결성"과 "되돌릴 수 있음"을 갖추지 못해서** 생깁니다. 따라서 우선순위는 화려한 기능보다 **번들 품질 → 롤백 → 기능** 순서여야 합니다.

### 6-2. 로드맵 (각 모듈의 **통과 기준**을 충족해야 다음으로 넘어감)

#### 모듈 1 — 개념
- **폐쇄망 제약:** 보이지 않는 다운로드(자동 업데이트, pip, 드라이버, 런타임)를 모두 찾아내는 것이 핵심 기술입니다.
- **오프라인 의존성:** "실행 파일 → 동적 라이브러리 → 드라이버/OS" 계층으로 생각합니다.
- **양자화:** 가중치를 4/8bit로 줄여 크기와 메모리를 줄이는 대신 품질이 약간 떨어집니다. 27B 기준 4bit ≈ 15~17GB, 8bit ≈ 28~30GB, 원본 bf16 ≈ 54GB **[가설]**.
- **KV 캐시:** 컨텍스트 길이에 비례해 늘어나는 메모리입니다. 하이브리드 모델은 일부 레이어만 KV 캐시를 쓰므로 증가 폭이 작지만 0은 아닙니다.
- **망간 전송:** 원본 → 매체 → 대상의 3지점 해시가 기본입니다.
- ✅ **통과 기준:** 진단 1·5번을 스스로 설명할 수 있다.

```powershell
.\llama-server.exe -m D:\models\<model>-Q4_K_M.gguf -c 16384 -ngl 99 --jinja --host 127.0.0.1 --port 8080
```
- ✅ **통과 기준:** 위 명령의 각 줄이 무엇을 하는지, 실패하면 어떤 증상이 나는지 말할 수 있다.

### 세 가지 핵심 검증
1. **"인터넷 없이 설치"가 모든 단계에 일관되게 반영됐는가?** — 처음 초안에서 빠진 부분이 있었습니다. **(a) LM Studio 런타임이 별도로 온라인 업데이트된다는 점, (b) `pip install huggingface_hub`는 온라인 준비 단계에서만 쓴다는 점, (c) gguf-dump 등 검증 도구도 폐쇄망에서 쓰려면 반입 대상이라는 점**입니다. 이를 반영했습니다. 폐쇄망 단계 명령은 모두 매체 위의 파일만 사용합니다.
2. **연습(Windows)과 실전(Mac)의 차이가 위험이 되는 지점을 숨기지 않았는가?** — 형식·엔진·드라이버·성능이 모두 다르다는 점을 명시했고, 대안(Mac 리허설, GGUF 공유)을 제시했습니다. 남은 위험: **GGUF를 공유해도 MLX 경로는 Windows에서 검증할 수 없습니다.** 이것은 해결된 것이 아니라 **줄인 것**입니다.
3. **실패 시 복구 절차를 실제로 제시했는가?** — 처음 초안은 원칙 위주였습니다. 아래 표에 구체적인 명령과 절차를 넣었습니다.
